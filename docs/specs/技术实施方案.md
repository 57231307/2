## 一、技术架构概述

### 1.1 架构选型

#### 1.1.1 架构模式
**模块化单体架构（Modular Monolith）**

选择理由：
- 开发团队规模中等（6-15人）
- 系统复杂度适中
- 便于快速迭代和部署
- 支持后期拆分为微服务

#### 1.1.2 技术栈总览

| 层次 | 技术选型 | 说明 |
|------|----------|------|
| 前端 | Angular 22 | 现代前端框架，TypeScript原生支持 |
| 后端 | NestJS 10 | TypeScript后端框架，依赖注入 |
| 数据库 | PostgreSQL 15 | 关系型数据库，支持JSONB |
| 缓存 | Redis 7 | 高性能缓存和消息队列 |
| ORM | TypeORM | TypeScript ORM，支持迁移 |
| 认证 | JWT + Passport | 无状态认证 |
| 文档 | Swagger/OpenAPI | API文档自动生成 |
| 日志 | Winston | 结构化日志 |
| 部署 | Docker + Docker Compose | 容器化部署 |

## 三、数据库设计

### 3.1 数据库选型

**PostgreSQL 15**

优势：
- 支持JSONB类型，适合灵活扩展
- 强大的索引功能，支持全文搜索
- 支持分区表，优化大表性能
- 事务完整性保证
- 丰富的统计函数

### 3.2 表分区策略

针对大数据量表（订单表、库存流水表），采用时间分区：

| 表名 | 分区策略 | 分区单位 |
|------|----------|----------|
| sales_orders | 按月分区 | month |
| purchase_orders | 按月分区 | month |
| inventory_transactions | 按月分区 | month |
| production_orders | 按月分区 | month |

### 3.3 索引策略

#### 3.3.1 主键和唯一索引
- 所有表使用UUID作为主键
- 业务编码字段创建唯一索引

#### 3.3.2 业务索引
- 常用查询字段创建索引
- 外键字段创建索引
- 状态字段创建索引

#### 3.3.3 复合索引
- 常见查询组合创建复合索引
- 遵循最左前缀原则

### 3.4 数据类型选择

| 业务场景 | 数据类型 | 说明 |
|----------|----------|------|
| 主键 | UUID | 全局唯一 |
| 编码 | VARCHAR(50) | 业务编码 |
| 金额 | DECIMAL(12,4) | 精确计算 |
| 日期时间 | TIMESTAMPTZ | 带时区 |
| 大文本 | TEXT | 备注等 |
| 结构化数据 | JSONB | 灵活扩展 |
| 枚举 | ENUM | 有限选项 |

## 四、API设计规范

### 4.1 RESTful API规范

#### 4.1.1 URL规范
```
资源：/api/v1/{resource}
子资源：/api/v1/{resource}/{id}/{sub-resource}
```

示例：
- GET /api/v1/products
- GET /api/v1/products/:id
- POST /api/v1/products
- PUT /api/v1/products/:id
- DELETE /api/v1/products/:id

#### 4.1.2 HTTP方法

| 方法 | 用途 | 示例 |
|------|------|------|
| GET | 查询 | GET /products |
| POST | 创建 | POST /products |
| PUT | 更新 | PUT /products/:id |
| DELETE | 删除 | DELETE /products/:id |

#### 4.1.3 响应格式

**成功响应：**
```json
{
  "success": true,
  "data": { ... },
  "message": "操作成功"
}
```

**分页响应：**
```json
{
  "success": true,
  "data": {
    "items": [...],
    "total": 100,
    "page": 1,
    "limit": 20,
    "totalPages": 5
  }
}
```

**错误响应：**
```json
{
  "success": false,
  "error": {
    "code": "PRODUCT_NOT_FOUND",
    "message": "产品不存在",
    "details": { ... }
  }
}
```

### 4.2 API版本控制

- URL版本：/api/v1/
- Header版本：Accept: application/vnd.api.v1+json

### 4.3 认证授权

#### 4.3.1 JWT Token
- Token有效期：7天
- Refresh Token：30天
- Token刷新机制

#### 4.3.2 权限控制
- 基于角色的访问控制（RBAC）
- 资源级别权限
- 操作级别权限

### 4.4 限流策略

| 接口类型 | 限制 |
|----------|------|
| 普通API | 100次/分钟 |
| 查询API | 200次/分钟 |
| 创建/更新API | 50次/分钟 |

## 五、安全方案

### 5.1 认证安全

#### 5.1.1 JWT配置
```typescript
jwt: {
  secret: process.env.JWT_SECRET,
  expiresIn: '7d',
  refreshExpiresIn: '30d'
}
```

#### 5.1.2 密码策略
- 最少8位
- 必须包含大小写字母和数字
- 密码加密：bcrypt（10轮）
- 90天强制修改密码
- 5次错误锁定账户

### 5.2 接口安全

#### 5.2.1 CORS配置
```typescript
{
  origin: ['https://erp.example.com'],
  credentials: true,
  methods: ['GET', 'POST', 'PUT', 'DELETE'],
  allowedHeaders: ['Content-Type', 'Authorization']
}
```

#### 5.2.2 CSRF防护
- CSRF Token验证
- SameSite Cookie

### 5.3 数据安全

#### 5.3.1 敏感数据加密
- 密码：bcrypt加密
- 敏感字段：AES加密
- 日志脱敏处理

#### 5.3.2 数据备份
- 每日全量备份
- 实时增量备份
- 异地容灾

## 八、事件驱动架构

### 8.1 事件类型

#### 8.1.1 领域事件
| 事件名 | 触发时机 | 说明 |
|--------|----------|------|
| ProductCreated | 产品创建 | 新产品创建事件 |
| OrderCreated | 订单创建 | 新订单创建事件 |
| OrderApproved | 订单审批 | 订单审批通过事件 |
| InventoryChanged | 库存变动 | 库存发生变化事件 |
| QualityChecked | 质检完成 | 质检完成事件 |

#### 8.1.2 事件处理
```typescript
@EventPattern('order.created')
async handleOrderCreated(@Payload() order: Order) {
  // 处理订单创建事件
  await this.notificationService.sendOrderNotification(order);
  await this.inventoryService.reserveStock(order);
}
```

### 8.2 消息队列

使用Redis作为消息队列：
- 订单创建 → 库存预留
- 订单审批 → 消息通知
- 库存变动 → 流水记录
- 质检完成 → 状态更新

```dockerfile

COPY nginx.conf /etc/nginx/nginx.conf
```

### 9.2 Docker Compose配置

```yaml
version: '3.8'

services:
  backend:
    build: ./backend
    ports:
      - "3000:3000"
    environment:
      - NODE_ENV=production
      - DB_HOST=postgres
      - REDIS_HOST=redis
    depends_on:
      - postgres
      - redis

  frontend:
    build: ./frontend
    ports:
      - "80:80"
    depends_on:
      - backend

  postgres:
    image: postgres:15-alpine
    environment:
      POSTGRES_DB: fabric_erp
      POSTGRES_USER: postgres
      POSTGRES_PASSWORD: ${DB_PASSWORD}
    volumes:
      - postgres_data:/var/lib/postgresql/data

  redis:
    image: redis:7-alpine
    command: redis-server --appendonly yes
    volumes:
      - redis_data:/data

  prometheus:
    image: prom/prometheus:latest
    volumes:
      - ./prometheus.yml:/etc/prometheus/prometheus.yml

  grafana:
    image: grafana/grafana:latest
    ports:
      - "3001:3000"
    volumes:
      - grafana_data:/var/lib/grafana

volumes:
  postgres_data:
  redis_data:
  grafana_data:
```

## 十一、开发规范

### 11.1 代码规范

#### 11.1.1 TypeScript规范
- 严格模式：strict: true
- 类型注解：必须显式声明类型
- 接口 vs 类型别名：优先使用interface

#### 11.1.2 命名规范
| 类型 | 规范 | 示例 |
|------|------|------|
| 类名 | PascalCase | ProductService |
| 接口名 | PascalCase | IProductRepository |
| 变量名 | camelCase | productList |
| 常量名 | UPPER_SNAKE_CASE | MAX_RETRY_COUNT |
| 文件名 | kebab-case | product.service.ts |

### 11.2 Git提交规范

使用Conventional Commits：

```
feat: 新功能
fix: 修复bug
docs: 文档变更
style: 代码格式
refactor: 重构
test: 测试
chore: 构建/工具
```

示例：
```
feat(product): 添加产品分类功能
fix(order): 修复订单状态更新问题
docs(api): 更新API文档
```

- 所有PR必须审查后才能合并

## 十二、技术风险及应对

### 12.1 风险清单

| 风险项 | 影响 | 概率 | 应对措施 |
|--------|------|------|----------|
| 数据迁移 | 高 | 中 | 制定详细迁移方案，充分测试 |
| 性能瓶颈 | 高 | 低 | 提前进行性能测试和优化 |
| 安全漏洞 | 高 | 中 | 定期安全审计和更新依赖 |
| 团队协作 | 中 | 中 | 制定代码规范，加强沟通 |
| 技术选型 | 中 | 低 | 技术选型充分论证 |

### 12.2 应急预案

1. **数据库故障**
   - 立即切换到备用数据库
   - 启动数据恢复流程

2. **服务宕机**
   - 查看日志定位问题
   - 重启服务
   - 回滚到上一版本

3. **数据丢失**
   - 停止写入，防止数据覆盖
   - 从备份恢复数据
   - 补录丢失数据
